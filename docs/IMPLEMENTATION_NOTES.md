

## Firebase Security Phase — 2026-09-18

### ما تم تنفيذه محليًا
- مراجعة قواعد Firestore الحالية مقابل خدمات التطبيق الفعلية.
- اعتماد Custom Claim `request.auth.token.admin == true` للأدمن الأعلى بدل `users.role`.
- إغلاق القراءة العامة لمستندات `users` وقصرها على صاحب المستند/الإدارة.
- تأمين `merchants` و`places` وطلبات الزيارة والتقييمات والكوبونات.
- منع إنشاء `visits` بشكل مستقل؛ الإنشاء الحالي يتم فقط ضمن Transaction تؤكد `visit_request` وتتحقق منها قواعد `getAfter()`. النقاط الحساسة تظل بحاجة إلى Backend قبل الإنتاج.
- جعل `audit_logs` Backend-only وغير قابلة للكتابة من التطبيق.
- فصل قواعد `tasks` للقراءة والإنشاء والتحديث والحذف حتى لا تستخدم `request.resource` في سياق القراءة.
- إبقاء أي Collection غير معرفة في القواعد مغلقة افتراضيًا.

### مهم قبل Firebase Publish
- هذه النسخة المحلية لا تعني أن القواعد نُشرت على مشروع Firebase.
- لا نحتاج Cloud Functions لتأكيد الزيارة في هذه المرحلة؛ لكن النقاط والتسويات المالية/المكافآت التي تغير رصيدًا يجب أن تنتقل إلى Backend موثوق قبل الإنتاج.
- لا يتم حذف بيانات Firestore الحالية.
- يجب اختبار التطبيق بعد النشر: تسجيل الدخول، قراءة الأماكن، إنشاء طلب زيارة، مسح QR، التقييم، الكوبون، المفضلة، المهام، والمكافآت.

## مراجعة ما قبل الاختبار — 2026-09-18 (مسار التنفيذ الحالي)

- تم اكتشاف تعارض بين `VisitService.confirmVisitRequest()` (Transaction من الهاتف) وبين قاعدة Firestore كانت تمنع إنشاء `visits` بالكامل. تم توحيد التصميم: الإنشاء الآن مسموح فقط عندما يكون `visit_request` نفسه قد تحول إلى `confirmed` داخل نفس Transaction، باستخدام `getAfter()`.
- أضيف `visitRequestId` إلى نموذج الزيارة لربط سجل الزيارة بمصدره. لا ينبغي إزالة هذا الحقل لأن قواعد Firestore تعتمد عليه.
- غُيّر `RatingService.submitRating()` ليعيد `ratingId` بعد نجاح Transaction، لأن الكوبون يجب أن يُربط بتقييم محدد وليس بمجرد مستخدم/مكان.
- أضيف `ratingId` إلى نموذج الكوبون. معرّف مستند الكوبون هو الكود المستخدم في الاسترداد، بينما `coupon_claims/{ratingId}` يمنع إصدار كوبون ثانٍ لنفس التقييم.
- `CouponService` لم يعد يعتمد على نص خصم يرسله التطبيق؛ يقرأ `discountOffer` من مستند المكان داخل Transaction، ثم ينشئ الكوبون المرتبط بالتقييم.
- أزيل getter العميل `AppUser.isAdmin` حتى لا تكون هناك واجهة برمجية تشجع على اعتبار `users.role` مصدرًا لصلاحية الإدارة. مصدر الصلاحية الأمني هو Rules/Custom Claims.
- تم تحديث README لأنه كان يحتوي تعليمات قديمة مثل حذف مجلد `lib` واستبدال المشروع وتذكر أن تسجيل الدخول خطوة مستقبلية. هذا لم يعد يعكس حالة المشروع الحالية.
- `audit_logs` ما زالت Backend-only في Rules. ملف `AuditLogService` موجود للتوافق/التوثيق لكنه غير مستخدم حاليًا، وأي استخدام جديد له يحتاج Backend موثوق.
- لم يتم تشغيل `flutter analyze` أو `flutter test` في هذه البيئة لأن Flutter/Dart غير متوفرين هنا. هذه نقطة اختبار الأحد وليست مدعاة لتغيير إعدادات المشروع الآن.
- صُحح تصميم الكوبونات مرة أخرى: Document ID للكوبون عاد إلى `code` لأن شاشة الاسترداد تبحث بالكود، وأضيفت مجموعة داخلية `coupon_claims/{ratingId}` كـ ledger يمنع إصدار أكثر من كوبون لنفس التقييم. يتم إنشاء claim والكوبون في Transaction واحدة.
- أصبح Document ID للتقييم مساويًا لـ `visitId`، مما يجعل التقييم المكرر لنفس الزيارة غير ممكن على مستوى البيانات، وليس فقط على مستوى الواجهة.
- تم تشديد إنشاء `visit_requests` بحيث لا يمكن أن يمتد وقت صلاحية الطلب لأكثر من 10 دقائق من وقت Firebase، وتشديد صلاحية الكوبون إلى حد أقصى 7 أيام.
- تم تشديد `reward_redemption_requests` ليتطابق `pointsCost` مع المكافأة النشطة نفسها بدل قبول قيمة يرسلها العميل دون تحقق.

- أضيفت معالجة أخطاء لشاشة توليد QR ومسح QR وإرسال التقييم حتى لا تبقى الواجهة في حالة تحميل دائمة عند `permission-denied` أو انقطاع الشبكة.

## 2026-09-19 — First-entry paths + quick device login + real weather
- The public first-entry screen is now `WelcomeRoleScreen`: Resident, Visitor, Service Provider.
- Resident and Visitor remain `role=user`; the selected experience is stored as `experienceMode`.
- Service Provider remains `role=merchant`; Admin is never selectable in the public UI.
- `EntryIntent` carries the first-screen choice safely through the Firebase sign-in transition without storing credentials.
- `AuthGate` now wraps authenticated sessions with `QuickAuthGate` when the user has enabled quick device authentication.
- Android quick authentication uses the OS `BiometricPrompt` and allows biometric authentication plus device credential (PIN/pattern/password). The app does not receive or store the device credential.
- Quick authentication can be enabled during first account setup or later from Settings.
- Home now shows a personalized greeting using the user's stored display name.
- Home category density was reduced to six visible categories plus `المزيد`.
- Current weather is fetched from Open-Meteo using the selected governorate's representative coordinates. If unavailable, the UI explicitly says it is unavailable rather than showing a fabricated value.
- `http` is now a direct dependency because weather retrieval is an application feature, not an accidental transitive dependency.
- The `CategoryScreen` accepts an empty category as the explicit `كل التصنيفات` mode used by `المزيد`.
- Testing limitation: this environment does not contain Flutter/Dart, so `flutter analyze`, `flutter test`, and APK build were not executed here. Android/Kotlin and Dart changes were reviewed structurally only.
